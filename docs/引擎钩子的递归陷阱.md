# 引擎钩子的递归陷阱——技能守护 × 缠怨卡死事故复盘

> 一句话原则：**包装（hook）某个引擎函数时，包装内部的任何判断都不能依赖这个函数本身所在的调用链**——
> 要用原始数据直读这类零耦合原语，否则在特定条件下会形成无限递归，卡死游戏。

## 一、事故现象

龙神赵云 1 血时质疑于吉〖蛊惑〗失败，游戏卡死（无报错弹窗、界面冻结）。

## 二、触发条件（三个条件缺一不可）

1. 本扩展的**技能守护**已生效（绝境⑥，包装了 `get.is.blocked` 等三个引擎函数）；
2. 质疑真牌的代价是"弃牌或失去 1 点体力，**并获得〖缠怨〗**"（`character/refresh.js` reguho_guess.contentx）；
3. 〖缠怨〗在体力≤1 时注册 skillBlocker 封锁其他技能（`refresh.js:13025`）。

1 血质疑失败 → 同时满足"获得缠怨"+"体力≤1" → 封锁器生效 → 下一次技能查询即死循环。

## 三、递归链详解

守护包装的持有判断原写法：

```js
const hasJuejing = (player) => player.hasSkill("gryjuejing");
```

`hasSkill` 不是数组查找，它要计算"当前生效技能列表"：

```
get.is.blocked(技能, 你)                 ← 引擎询问"此技能是否被封锁"
  └→ 守护包装先做前置判断 hasJuejing(你)
       └→ hasSkill("gryjuejing")        ← 需要计算生效技能表
            └→ player.getSkills()
                 └→ game.filterSkills()  ← 计算时要逐个检查封锁情况
                      └→ get.is.blocked("gryjuejing", 你)  ← 又进入守护包装 💥
```

**平时不炸的原因**：`game.filterSkills`（`noname/game/index.js` filterSkills）开头有短路——
`player.storage.skill_blocker` 为空时直接返回，`get.is.blocked` 根本不会被调用。
所以守护上线后一直正常，直到缠怨这类封锁器第一次挂到玩家身上。

## 四、修复方案

判断改为直查底层技能数组：

```js
const hasJuejing = (player) => player && Array.isArray(player.skills) && player.skills.includes("gryjuejing");
```

- `player.skills` 是引擎增删技能直接操作的原始数组（`removeSkill` 内部就是 `player.skills.remove(skill)`）；
- `Array.includes` 是纯数据读取，不触发任何引擎逻辑，不可能绕回被包装的函数——**递归环在起点断掉**；
- 语义上也更正确：`hasSkill` 回答"当前**生效**吗"（被封锁会答否），而守护需要的是"**拥有**吗"——
  固有武将技能查底层数组才是本意，即使被 exotic 效果暂时滤出生效列表，守护也应继续守。

否决的备选方案：
- **重入标志位**：能止血但治标，异步流程中易错，且掩盖设计缺陷；
- **去掉持有判断**：不行，判断的作用是把保护范围限定在龙神赵云身上。

## 五、沉淀的开发原则

1. **hook 的自引用禁令**：包装函数 `f` 时，包装体内不得调用任何"求值过程会经过 `f`"的接口。
   本例中 `get.is.blocked` 的包装内调用了 `hasSkill`，而 `hasSkill` 的求值链正好经过 `get.is.blocked`。
2. **判断用原始数据**：拦截器里的资格判断，优先用 `player.skills`、`player.storage`、事件字段等
   同步原始数据直读，而非引擎的复合查询 API。
3. **短路条件是隐形炸弹**：正常路径上有短路（无封锁器时不调 blocked）意味着 bug 平时完全潜伏，
   只有特定技能组合才引爆——第三方效果（缠怨/拜印类封锁器）× 自定义拦截的组合必须专项回归测试。
4. **排查手段**：F12（Ctrl+Shift+I）看 Console 红字堆栈可直接点名递归/报错源；
   扩展逐个禁用做隔离对照。
